## 修复结果

| 审计问题 | 修复行为 |
| --- | --- |
| 并发目标写入被覆盖 | PutObject、CompleteMultipartUpload 使用原子 If-None-Match；竞争写入保留目标并进入冲突处理 |
| 成功响应丢失后重试误报冲突 | 目标条件提交收到412后，复核源身份、元数据和完整SHA-256；正确已提交对象恢复为done，业务替换仍保留冲突，409仍为可重试失败 |
| 分片拼接不同源版本 | 清单与源 HEAD 核对，GET 使用 If-Match/可用 VersionId，提交前复核源身份 |
| 同大小错误内容误报完成 | 新复制目标、已有目标与 diff 均执行完整 SHA-256 校验；无法验证返回错误 |
| 内容一致但元数据不同 | 比较常见内容头、Expires、用户 metadata；迁移报告冲突，diff 报 metadata mismatch |
| 删除后对象复活 | 显式要求外部冻结源数据集变更及相关业务删除；提交前检测已完成源删除。没有把客户端检查宣称为跨集群原子删除机制 |
| 换端点复用状态库漏迁 | 持久化源/目标端点和桶身份；scanner 也绑定实际客户端源端点；不匹配直接拒绝 |
| 未扫描或中断扫描误当完整 | 持久化扫描 generation，仅完整成功的扫描允许 migrate |
| 源同 key 更新后保留旧 done | 源身份变化后重新进入 pending，再验证目标，仍不赋予覆盖权限 |
| 多进程误用状态库 | SQLite 独立任务锁排除第二 writer，允许只读 status；子进程被 kill 后锁可释放 |
| 复制失败/取消仍成功 | 聚合对象失败并返回错误；取消和本地持久化故障返回非零，后者取消工作池 |
| 目标404或网络错误被写成源缺失 | 保留源/目标错误来源，仅真实源 NoSuchKey 可 skipped；不再从 URL/错误文本猜测404 |
| diff 权限错误后卡住 | 首个致命错误取消生产者和 worker，退出并返回根因 |
| 空目标桶缺失未发现 | diff 检查两端桶；权限/不存在均失败 |
| 非美东区域建桶错误/他人桶误接受 | 传 LocationConstraint；只容忍已归属自身且再次 HEAD 成功的创建竞态 |
| 特殊 key 和损坏分页 | 请求 URL 编码、解码一次；验证 key/size/IsTruncated/token；不认证缺结束标志的扫描 |
| 配置拼写和整数溢出 | YAML 严格字段与单文档解析；先限长再乘；并发/分片资源上限；端点和桶名防误用检查 |
| 全桶状态文件名冲突 | 派生路径保留配置 basename，status 使用相同规则发现文件 |
| 无界分片缓冲 | 精确范围和长度校验、限读；分片落磁盘，避免完整分片驻留内存 |
| 网络永久停滞 | 响应头30秒；每次阻塞正文读取/连接写入90秒；使用 HTTP/1 保证上传连接超时可控 |
| 冲突日志与状态持久化顺序 | key 转义，日志 Sync 后才提交 conflict；新日志权限0600 |
| 旧依赖与构建工具链告警 | S3 SDK v1.97.3、eventstream v1.7.8、x/sys v0.44.0；Go 1.26.10 工具链 |
| 原有并发测试时序不稳定 | 同步屏障替代固定40ms sleep，验证两个分片实际并行及最终内容 |

审计用例已进入默认回归测试，不再需要 `-tags audit`。额外测试包括真实子进程崩溃释放锁、源响应身份变化、相同 ETag 不同内容、同长度目标损坏、异常 Range、元数据冲突、网络读写停滞、低速读取间隔、损坏报告输出和清单分页缺失标志。

## 历史真实服务记录：RustFS 1.0.0-alpha.61

此前对本机已有 RustFS `1.0.0-alpha.61` 启动两个独立临时实例，执行扫描、迁移、重试、SHA-256读回和diff。以下是该旧版本的历史结果，不是 `1.0.4` 的测试结果，也不能据此推断 `1.0.4` 通过或失败。

- empty、hello.txt、含中文/空格/特殊字符 key 的3个对象成功，目标读回 SHA-256 一致。
- 两个分片对象仍因该版本 CompleteMultipartUpload 的带引号 ETag 兼容问题返回 InvalidPart。
- folder/ 的源端带 VersionId GET 返回 InvalidArgument；这是新版迁移严格固定源身份后暴露的旧服务版本读取兼容限制。
- 这些失败现在保留为 failed，并使 Migrator.Run 明确返回错误；重跑仍失败，不会被记成 done 或 skipped。最终 diff 报3个缺失。

历史原始证据：[alpha.61 运行日志](../audit-results/fix-real-rustfs.log)。**当时不能批准该旧服务版本的完整生产迁移。** 此限制针对上述旧版本与历史运行；`1.0.4` 的实际结果以上一节为准。其他拟部署的 RustFS/MinIO/AWS S3 版本仍需分别验证，尤其是条件写、分片完成、版本读取和元数据。未通过时应升级或修复服务端，不应通过删除条件、关闭校验或只比较大小绕过。

## 升级与运行要求

1. Go构建环境升级到1.26+，默认工具链1.26.10；阅读更新后的README和配置示例。
2. 对有处理记录的旧无身份状态库，使用新的状态目录完整重扫。程序重新验证现有目标内容，不要求删除目标数据。
3. 从扫描开始冻结源写入、删除及生命周期变更，并暂停迁移 key 在目标端的业务删除，或使用外部可靠墓碑协调。随后显式使用 `--source-frozen` 或设置 `source_frozen: true`；该参数不会自动冻结任何服务。
4. 目标端必须正确实现原子条件写；仅发出HTTP条件头不能补救一个忽略条件的服务端。源码回归通过不等于所有 S3 实现都已验证。
5. `diff` 现在完整读取双端正文，并检查保留元数据，需要 GetObject 权限和读带宽；当前不受 run/migrate 的 rate-limit 限制。分片迁移通常读源两遍、读目标一遍，临时盘需留足容量。
6. `run` 的零退出表示没有传输失败，不代表所有源数据已迁入；conflict/skipped 仍需处置，最终必须审阅状态并运行diff。最终验收期间相关数据应保持稳定；独立对象读回不是跨集群原子快照。

同URL后端被重建、DNS切换到另一集群、或凭证切换租户不一定能由端点字符串区分，应使用新状态目录。恢复仍为对象级重试；硬杀残留分片依赖服务端清理生命周期。版本历史、删除标记、tags、ACL、Object Lock、桶策略等仍不在工具迁移范围。

本次没有执行生产规模压力、主机断电、真实KMS/STS权限矩阵或所有服务版本认证；这些部署验收不能由本机单元测试替代。
