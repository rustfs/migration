## 必须优先处理的风险

以下均为 P1，即生产迁移放行前应解决的问题；排序优先考虑业务数据破坏和错误验收。

### A01 并发写入可覆盖目标业务数据

位置：`internal/migrator/migrator.go:198`、`:307`、`:480`。

目标 HEAD 返回 404 后，业务可能写入同名 key；随后的 PutObject 或 CompleteMultipartUpload 是无条件写，覆盖刚写入的业务数据。两条路径均已复现，覆盖后状态仍为 done。增加一次 HEAD 无法消除这个时间窗口。

证据：`TestAuditConcurrentTargetWriteMustNotBeOverwritten`，单 PUT 和分片完成两个子例失败。

修复：在真正提交目标对象时使用服务端原子 `If-None-Match: *`，正确处理 412 和 409，验证 RustFS/MinIO/S3 对这两个 API 的支持；目标不支持时，应拒绝提供“在线永不覆盖”保证。当前 SDK `service/s3 v1.58.2` 的两个输入结构没有该字段，需要升级 SDK 或实现经过验证的签名中间件。[AWS 条件写说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

### A02 大对象可能由不同源版本拼接而成

位置：`internal/migrator/migrator.go:437`、`:497`。

分片 Range GET 没有固定 VersionId 或 If-Match。测试在第一片读完后把源对象由全 A 更新为全 B，得到 10MiB 的 A/B 拼接对象；目标总长度正确，状态为 done，但内容不是任何一个完整源版本。

证据：`TestAuditMultipartSourceMutationMustNotCommitMixedVersions`。

修复：固定每个对象的源版本，或对 HEAD/GET/所有 Range 使用同一 ETag 条件；遇 412 失效整次传输，不能继续拼接。单 PUT 也应检测扫描到读取之间的源身份变化，并更新/失效清单记录。分片完成后还须做内容摘要验证。

### A03 应用双端删除后对象会复活

位置：`internal/migrator/migrator.go:275`、`:307`；关联 `docs/DESIGN.md` 的线上双读双删假设。

迁移先读完旧对象，应用随后删除源和目标，迁移仍把已读数据写回目标。测试确认源对象已消失、目标被重新创建并标为 done。

证据：`TestAuditConcurrentDeleteMustNotResurrect`。

修复：引入删除墓碑、可靠删除事件回放或应用写入协调，或在迁移窗口冻结删除。**仅增加条件写不能解决本项**：删除后目标不存在，`If-None-Match: *` 仍会成功。

### A04 大小相同被误当成内容已验证

位置：`internal/migrator/migrator.go:555`、`:497`；`internal/differ/differ.go:111`。

已有目标只要大小相同，而 ETag 为 multipart 或为空，就会被判断为已迁移；diff 同样计入 OK。新传输的分片对象也只验总长度。故“已有同尺寸但错误的对象”“源混版”“传输中同尺寸损坏”均可能逃过验收。

证据：`TestAuditUnverifiableTargetMustNotBeConsideredMigrated` 的 4 个子例，以及 `TestAuditDiffDoesNotCertifySameSizeCorruption`。后者构造合法 5MiB+8 字节对象及真实两分片 ETag，目标改坏一字节后仍得到 `OK=1`、无 gaps。

这是文档已描述的 size-only 降级策略，但不足以满足可靠迁移验收。修复应引入完整对象摘要或读回校验，无法验证的对象单列 unverified，不能标 verified/done。跨服务使用 checksum 时必须区分算法、完整对象与复合分片摘要。无连字符的 ETag 也不必然是可跨端比较的 MD5，SSE-KMS/SSE-C 是典型例外。[AWS ETag 语义](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html)

### A05 更换目标复用断点库会静默漏迁

位置：`internal/store/store.go:58`、`:146`、`:163`；`internal/config/config.go:359`。

DB 只绑定 bucket 名，没有源/目标身份。向目标 A 完成后，把配置改成目标 B 并复用 DB，重新 scan/run 仍忽略 done 行，返回成功、processed=0，而 B 缺少数据。

证据：`TestAuditResumeRejectsDifferentDestination`。

全桶模式还忽略 `db_path` 的文件名，使用同目录的 `migration-<bucket>.db`；仅将 `/state/job-A.db` 换成 `/state/job-B.db` 不能隔离任务。

修复：持久化迁移任务身份、源/目标规范化地址与账户/集群身份、bucket、清单 generation；恢复前验证一致，不一致则拒绝。暂时必须每个迁移任务使用独立状态目录。

### A06 复制失败仍返回成功

位置：`internal/migrator/migrator.go:259`、`:164`；`cmd/root.go:374`。

markFailed 写 DB 成功后返回 nil，Run 未汇总失败对象。真实 Cobra run 测试中，源 GET403、failed=1、done=0、目标缺对象，命令仍返回 nil，进程会退出 0。隔离 RustFS 分片失败也出现相同行为。

证据：`TestAuditRunReportsObjectFailure`。

修复：可以继续处理其他对象，但最终返回包含 failed/pending/unverified 的结构化未完成结果和非零退出码。conflict/skipped 应有明确验收策略，不能仅凭命令 exit 0 下线源集群。

### A07 目标端 404 被误判为源对象不存在

位置：`internal/migrator/migrator.go:229`。

copy 的全部错误经同一 IsNotFound 分支处理，目标 PutObject、CreateMultipartUpload、CompleteMultipartUpload 或验收 HEAD 的 404 都被写成 `skipped / source 404`。普通 migrate 只处理 pending/failed，因此不会重试；重新扫描可能恢复，但错误的 skipped 会误导操作员。

证据：`TestAuditTarget404MustRemainRetryable` 的 4 个阶段子例。

修复：错误必须携带源/目标及操作类型；只有确认来自源 GET/HEAD 的对象缺失才能 skipped。桶缺失与对象缺失也应分别处理。

### A08 diff 遇权限错误可能永久阻塞

位置：`internal/differ/differ.go:119`、`:160`。

worker 遇 HEAD403 等致命错误后直接退出；同页生产者仅等待 jobs 或外部 ctx。工作队列满且 worker 已退出时，生产者不会再检查 fatal。测试用 10 个对象、workers=1 即可复现，必须外部取消才释放。默认并发在足够多错误对象时同样可能触发。

证据：`TestAuditDiffReturnsOnHeadFailure`。

修复：派生可取消 context；首个致命错误同步取消生产者和 worker，等待全部退出后返回根因。

### A09 网络错误文本中的 key 可被误认作 404

位置：`internal/s3client/errors.go:90` 到函数末尾。

未得到结构化 APIError 时，用错误字符串包含 NotFound/NoSuchKey/NoSuchBucket 判断不存在。网络断连的 URL 若含这些 key 片段，就被错误分类。目标 HEAD 由此绕过“确认不存在”的检查，或源 GET 被永久 skipped。

证据：`TestAuditTransportFailureIsNotObjectNotFound` 的 3 个 url.Error 子例。

修复：仅依据结构化 S3 错误和实际 HTTP 状态；网络/协议错误不得通过任意字符串猜测对象是否存在。

## 静态审查发现的资源和恢复风险

这些项目有代码依据，但未全部进行压力、断电或硬杀复现，不能与上面的确定性缺陷测试混称。

- `migrator.go:446` 对 Range 响应直接 io.ReadAll，没有限读，也不验证 Content-Range/预期分片长度。服务端或代理忽略 Range 时可能将整个大对象读入内存；最终大小核验发生在提交之后。应检查范围、限制读取到 partLength+1，拒绝异常响应。
- 默认原始分片缓冲约为 `16 workers × 4 parts × 16MiB = 1GiB`，不含 ReadAll 扩容、SDK 与 HTTP 开销。自动放大分片大小后资源继续增长；没有全局字节预算、磁盘空间预检、part size 上限。并发数量有限不等于内存占用足够安全。
- `s3client/client.go:42` 未设置 HTTP 总超时，默认 Transport 无响应头超时，命令 context 主要依赖信号取消。对连接已建立但永久不返回的数据/头部，需要可配置请求超时和读停滞检测；不可只设一个会误杀正常大对象的短总时限。
- 分片 uploadId/已完成 parts 未持久化；重启会重新创建上传。进程被 kill -9 时无法执行 abort，残留分片须依赖服务端明确配置的清理生命周期。当前“断点恢复”是对象级重试，不是分片级续传。
- SQLite WAL 使用 synchronous=NORMAL；正常关闭重开已测，断电后的最后事务持久性未验证。conflict.log 与 DB 不在同一事务中，日志无 fsync，key 未转义 TSV 换行/制表符。建议用 DB 作为权威事件记录，导出 JSONL 并保留校验信息。
- 未设置跨进程任务锁；文档明确不支持多进程共享 DB。状态没有 claim/lease，应主动拒绝第二实例以防误操作。
- HTTP 明文 endpoint 被允许；示例采用 HTTP。跨不可信网络部署必须配置 HTTPS。静态凭证 provider 的 session token 固定为空，不能据此宣称完整支持 STS 临时凭证。该项是部署/能力限制。

## S3 语义与兼容边界

当前迁移保存对象内容、常见内容头和用户 metadata；未迁移版本历史、删除标记、Object Lock、桶策略、生命周期等。README 已明确排除其中多项，不能把这些都算作未声明缺陷。

对象 tags、ACL、存储等级、SSE 配置、retention/legal hold 不在当前复制参数中；依赖它们的访问控制、合规保留或存储策略不能仅通过内容拷贝保持。已有目标“大小和 ETag 匹配”时也不会核对 metadata。上线前需对实际使用的 S3 功能做清单，明确迁移、拒绝或另行配置，不应承诺完整复制全部 S3 语义。

**隔离服务实测的具体范围：** 本机安装的是 RustFS `1.0.0-alpha.61`（commit `7622b37f7be3e7e83a2a3fbfc5547e18930cce55`，2025-10-07 构建），不是最新服务端。脚本启动两个临时目录和回环端口的独立实例，执行扫描、迁移、重跑、目标读回 SHA-256 与 diff，完成后停止进程并清除临时数据。

- `empty`、`hello.txt`、`中文/空 格+%?#.txt`、`folder/` 四个对象内容 SHA-256 一致，迁移保留了源响应中可见的 Content-Type、audit metadata 和 Cache-Control 值。
- 源服务的基线 GET 已把 Cache-Control 暴露为用户 metadata 而非标准响应字段；这不是本次证实的迁移工具新增丢失。
- 5MiB 边界对象和 11,200,000 字节对象都在 CompleteMultipartUpload 返回 InvalidPart：服务端期望无引号 ETag，而收到带引号 ETag。两次运行均失败，最终 `Done=4, Failed=2`，但 Migrator.Run 仍 nil；diff 正确报 Missing=2。
- 这是指定旧版服务端与当前客户端的兼容性失败，不能直接归因于最新 RustFS，也不应据此全局去掉 ETag 引号作为通用 S3 修复。应在拟部署的服务端版本上复测并修复对应兼容层。

现有 fake S3 不充分校验分片最小尺寸、Complete manifest、条件写及 abort 清理；Range 分支在发出 206 后才设置部分响应头，key 解析还会裁剪尾斜杠/重复解码。因此 mock 测试通过不能替代真实协议兼容矩阵。

## 依赖与工具链

`go.mod` 的 S3 SDK 为 v1.58.2、eventstream 为 v1.6.3。govulncheck 源码扫描报告 GO-2026-5764；官方修复版本包含 eventstream v1.7.8、S3 v1.97.3。该问题是 EventStream 解码拒绝服务，当前代码未直接调用 SelectObjectContent，工具调用图告警不等于本次已证明迁移流程可被该漏洞攻击。仍建议成组升级兼容的 AWS SDK 依赖并重跑协议测试。[AWS 安全公告](https://github.com/aws/aws-sdk-go-v2/security/advisories/GHSA-xmrv-pmrh-hhx2)

扫描工具 v1.9.0 自动使用 Go 1.26.10，源码扫描因此检测的是该工具链标准库，不能替代本机 Go 1.24.1 构建产物检查。对实际生成二进制另做了 `-mode binary` 扫描，工具报告 45 项符号级告警及其他包/模块告警，包括旧 Go 标准库。二进制扫描是保守匹配，包含与客户端迁移路径无关的服务端功能，**不是已确认 45 个可利用漏洞**。应使用受支持且已修补的 Go 工具链构建，升级依赖后再做可达性分析。Windows x/sys 模块告警也不能直接算成本次 darwin 平台可利用问题。

## 修复顺序与生产验收条件

1. 先解决 A01–A04 的数据安全：目标条件写、固定源版本、删除协调、完整内容验证；同步收紧文档承诺。
2. 解决 A05–A09 的状态与控制流：任务绑定、完整扫描 generation、明确错误来源、非零失败/取消退出码、diff 全链路取消。
3. 补严格配置、桶存在/区域/归属校验、合法 key 编码、资源预算、超时、上传残留清理与任务锁。
4. 固定拟部署服务端和 SDK/Go 版本，在 RustFS、MinIO、AWS S3 实际使用组合上运行相同验收矩阵。
