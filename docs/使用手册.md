# migration 中文使用手册

安全的单向 S3 迁移工具：从来源集群复制对象到目标集群。适用于 RustFS、MinIO 以及其它 S3 兼容存储。

**永不覆盖目标上已有对象。永不删除任何一侧的数据。中断后续跑即可。**

---

## 1. 你只需要记住两条命令

```bash
cp config.example.yaml config.yaml   # 填写来源 / 目标地址和密钥
./bin/migration run  -c config.yaml  # 扫描 + 复制
./bin/migration diff -c config.yaml  # 核对来源是否都到了目标
```

`config.yaml` 里 `bucket:` 留空，就会迁移来源上的**每一个桶**。只迁一个桶时写成 `bucket: photos`，或命令行加 `--bucket photos`。

查看全部帮助（中英双语）：

```bash
./bin/migration --help
./bin/migration run --help
./bin/migration diff --help
```

---

## 2. 安装与编译

需要 Go 1.22+。纯 Go SQLite，**不需要 CGO**。

```bash
git clone https://github.com/rustfs/migration.git
cd migration
CGO_ENABLED=0 go build -o bin/migration .
# 或
make build
```

得到静态二进制 `bin/migration`。

---

## 3. 配置

```yaml
old:                              # 来源（只读）
  endpoint: "http://10.0.0.1:9000"
  access_key: "OLD_AK"
  secret_key: "OLD_SK"
  region: "us-east-1"

new:                              # 目标（读 + 写，需要能 CreateBucket）
  endpoint: "http://haproxy.new.local:9000"
  access_key: "NEW_AK"
  secret_key: "NEW_SK"
  region: "us-east-1"

bucket: ""                        # 空 = 全部桶
db_path: "./migration.db"
conflict_log: "./conflict.log"
spool_dir: ""                     # 小对象临时目录，默认跟 db 同目录

workers: 16                       # 同时拷贝的对象数，默认 16
multipart_threshold: 52428800     # ≥ 50MiB 走分片上传
multipart_part_size: 16777216     # 16 MiB。非末片必须 ≥ 5 MiB（5242880）；更小会在加载配置时失败
multipart_concurrency: 4          # 单个大对象的并行分片数，默认 4
```

没有 `bandwidth` / `rate_limit` 这类 MB/s 字段。要降低网络或 API 压力，调小 `workers`（大对象再调小 `multipart_concurrency`），详见 [§9.1](#91-限速与并发)。

地址一律按 **path-style** 访问（自建 RustFS / MinIO 的常见方式）。

环境变量会覆盖 YAML，适合容器或密钥管理：

`OLD_ENDPOINT` `OLD_AK` `OLD_SK` `OLD_REGION`  
`NEW_ENDPOINT` `NEW_AK` `NEW_SK` `NEW_REGION` `REGION`  
`BUCKET` `DB_PATH` `CONFLICT_LOG` `SPOOL_DIR`

## 4. 命令说明

| 命令 | 作用 | 是否写目标 |
| --- | --- | --- |
| `migration list -c config.yaml` | 列出源集群全部桶 | 否 |
| `migration run -c config.yaml` | **推荐**：先扫描再复制 | 是（但不覆盖） |
| `migration scan -c config.yaml` | 只扫描，写入本地 SQLite | 否 |
| `migration migrate -c config.yaml` | 只复制 SQLite 里 pending/failed 的对象 | 是 |
| `migration status -c config.yaml` | 看本地进度，不访问 S3 | 否 |
| `migration diff -c config.yaml` | 按源清单对目标做 HEAD，查缺失和不一致 | 否 |
| `migration diff --extra -c config.yaml` | 同上，并列出**仅目标上有**的 key | 否 |

通用参数：

- `-c, --config` 配置文件，默认 `config.yaml`
- `--bucket NAME` 覆盖 YAML 里的桶名
- `--help` 中英双语帮助
- `--version` 版本号

## 5. 推荐操作流程

### 5.1 全量迁移（最常用）

```bash
./bin/migration list -c config.yaml          # 确认能连上来源
./bin/migration run  -c config.yaml          # 扫描并复制全部桶
./bin/migration status -c config.yaml        # 看进度
./bin/migration diff -c config.yaml          # 确认源上的对象都在目标上
```

`run` 对每个桶会：

1. 检查源桶存在（`HeadBucket`）
2. 目标没有该桶则创建（已有则不动）
3. `ListObjectsV2` 全量扫描，写入 SQLite
4. 对每个 pending / failed 对象：先 `HeadObject` 目标。不存在则 GET 来源、PUT 目标。已存在且与清单一致（大小相同；两边都有 ETag 且都不是分片 ETag `xxx-N` 时，ETag 也相同）记为 `done`，不再上传。已存在但不一致则写入冲突日志，不覆盖
5. 校验大小；单分片对象再比 ETag

### 5.2 只迁一个桶

```bash
./bin/migration run -c config.yaml --bucket photos
```

### 5.3 增量补拷（源上后来新写入的对象）

S3 的 List 接口**不能**按修改时间在服务端过滤。正确做法是再扫一遍全量清单：

```bash
./bin/migration scan    -c config.yaml   # 新 key 变成 pending；曾经 skipped 后又出现的也会重试
./bin/migration migrate -c config.yaml
./bin/migration diff    -c config.yaml
```

或直接再跑一次 `run`（已 `done` / `conflict` 的行不会被覆盖重传）。

### 5.4 中断后续跑

第一次 `Ctrl-C` 优雅停止（进行中的分片会 Abort，SQLite 已落盘）。再按一次强制退出。

若中断发生在目标 `PutObject` 已成功、SQLite 尚未写成 `done`，该行会停在 `failed`，但目标上已经有对象。下次 `migrate` 看到大小一致，且可比的 ETag 也一致时，记为 `done`，而不是 `conflict`。只有大小不同或可比 ETag 不同才算冲突，并且仍然不会覆盖。

```bash
./bin/migration migrate -c config.yaml    # 只重试 pending / failed
```

### 5.5 先盘点、再决定是否拷

```bash
./bin/migration scan   -c config.yaml
./bin/migration status -c config.yaml     # 看有多少对象、多大
# 确认后再
./bin/migration migrate -c config.yaml
```

## 6. 状态机（每个对象一行）

| 状态 | 含义 | 再扫会刷新吗 |
| --- | --- | --- |
| `pending` | 待拷 | 会更新 size/etag |
| `failed` | 上次失败，`migrate` 会重试 | 会回到 pending |
| `skipped` | 拷的时候源已 404（应用删了） | **会**回到 pending（对象后来又出现时） |
| `done` | 已拷到目标并校验，或目标上已有与清单一致的对象 | 不会动 |
| `conflict` | 目标已有同名对象，且与清单不一致（大小或可比 ETag 不同），未覆盖 | 不会动 |

冲突行写入 `conflict.log`（TSV）：

```
<object-key>	<source-LastModified>	<target-LastModified>
```

单桶模式使用你配置的 `db_path` / `conflict_log`。全桶模式自动变成：

- `migration-<桶名>.db`
- `conflict-<桶名>.log`

## 7. diff 怎么读

```text
=== diff photos ===
ok=1000  missing=2  size_mismatch=0  etag_mismatch=1  extra_on_target=0
一致=1000  缺失=2  大小不一致=0  ETag不一致=1  仅目标有=0
  missing  a.txt  not on target
  etag     b.txt  src=abc dst=def
```

- **missing**：源有、目标没有 → 再跑 `migrate` 或 `run`
- **size / etag**：两边同名但内容对不上（目标可能被别的写入改过；本工具不会覆盖）
- **extra_on_target**（需 `--extra`）：只在目标上，通常是业务已经写到新集群，**不算失败**

有 missing / size / etag 时退出码为 `1`。

## 8. 安全保证

| 保证 | 做法 |
| --- | --- |
| 永不覆盖目标对象 | 写之前强制 `HeadObject` |
| 永不删除 | 代码里没有 `DeleteObject`（分片失败只 `AbortMultipartUpload`） |
| 不走错桶 | `HeadBucket` + 每页 Name 校验 + SQLite 绑定桶名 |
| 源中途被删 | 记 `skipped`，不当失败 |
| 崩溃可续 | 每对象状态在 SQLite WAL |
| 内存有上限 | 小对象落盘；大对象按分片读 |
| 拷后校验 | 比 size；单 part 再比 ETag |

## 9. 调优与注意

### 9.1 限速与并发

本工具**没有**按 MB/s 限速的配置。`config.yaml` 里不存在 `bandwidth`、`rate_limit` 字段，环境变量里也没有对应项。吞吐只由并发控制：

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `workers` | 同时在拷贝的对象数。`diff` 对目标做 HEAD 时也用这个并发 | 16 |
| `multipart_concurrency` | 单个大对象里并行上传的分片数（只在 `run` / `migrate` 的分片路径上） | 4 |

峰值大约是 `workers × multipart_concurrency`。小对象每个只占一路；达到 `multipart_threshold` 的大对象会按分片把并发乘上去。默认 `16 × 4` 很容易打满网卡、源或目标集群，以及前面 HAProxy 的 `maxconn`。

希望把流量压到大约 20 MB/s 这一档时，先把 `workers` 调小。大对象仍然占满链路时，再把 `multipart_concurrency` 调小。改完看 `migration status` 的本地进度，并在机器上看网卡和集群负载（`status` 本身不访问 S3），按观察结果继续加减。实际 MB/s 取决于对象大小和链路，配置里写不出一个「等于多少 MB/s」的数。

```yaml
# 降负载的起点。先跑一小段，再按 status 和网卡调整。
workers: 2
multipart_concurrency: 2
```

链路有余量、想更快时反过来：小文件多就加大 `workers`；单个大文件就加大 `multipart_concurrency`，或减小 `multipart_part_size`（单位字节，默认 16 MiB，不能小于 5 MiB）。

`multipart_part_size` 必须 ≥ 5 MiB（5242880）。S3 / RustFS 规定除最后一片外每片至少 5 MiB，否则上传返回 `EntityTooSmall`。默认 16 MiB 已满足，不会改。配置写得更小则在加载时直接报错，不会把数值悄悄抬到 5 MiB。

### 9.2 其它注意

- `/tmp` 若是内存盘，把 `spool_dir` 指到真实磁盘
- SQLite 单文件不要多进程同时写同一个 `db_path`
- 不迁移：版本历史、删除标记、Object Lock、桶策略、生命周期规则
- 不要按「启动时间窗口」自己做增量，List API 做不到；请全量再扫

SQLite 存的是元数据（key/size/etag/状态），几千万行通常没问题。对象过亿时本工具用 keyset 分页拉 pending，内存仍然受控。多台机器同时迁同一批对象需要以后换独立数据库，当前版本是单机。

## 11. 常见问题

| 现象 | 处理 |
| --- | --- |
| 想把速度限在大约 20 MB/s | 没有 MB/s 参数。调小 `workers`（大对象再调小 `multipart_concurrency`），看 `status` 和网卡。见 §9.1 |
| `old.endpoint is required` | 检查 YAML 或 `OLD_ENDPOINT` |
| `multipart_part_size must be >= 5242880` | 分片小于 5 MiB。改成 ≥ 5242880（默认 16 MiB）。工具不会自动抬高 |
| `head bucket "…" on source` | 桶不存在、地址错、或密钥没有读权限 |
| `create bucket … on target` | 目标密钥缺少 `s3:CreateBucket` |
| 大量 `etag mismatch` | 源端 SSE/压缩会改 ETag；可把 `multipart_threshold` 调低走分片（只校验 size），或人工抽查 |
| `db_path is bound to bucket "X"` | 一个 db 只绑定一个桶，换路径 |
| `database is locked` | 不要对同一 db 起两个进程 |
| Ctrl-C 退不出 | 等当前分片结束，或再按一次 |
| diff 还有 missing | 再 `migration migrate`；看 `failed` 行的 `last_error` |

## 12. 和生产架构的关系

典型场景：旧集群只读历史数据，新集群承接全部写入；应用双读。本工具把旧集群上「目标还没有的 key」补过去，**不会**把新集群上更新的对象打回旧内容。

因此：同名但与清单不一致才是冲突，请看 `conflict.log`，不要改成覆盖模式。与清单大小（以及可比 ETag）一致的目标对象会记为 `done`。
