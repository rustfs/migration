# S3 对象迁移使用手册

## 迁移前提

源集群在扫描、迁移和最终验收期间必须冻结写入与删除，包括应用双删和生命周期删除。 迁移清单对象在目标端的业务删除也必须暂停或通过删除墓碑协调；仅禁止旧集群删除不能阻止历史对象被重新写入目标。`source_frozen: true`、`SOURCE_FROZEN=true` 或 `--source-frozen` 只是声明已经完成外部冻结，不会替你修改桶权限或停止应用。

目标集群必须原子实现 PutObject、CompleteMultipartUpload 的 `If-None-Match: *`。程序对已有目标执行内容校验或报告冲突，不主动覆盖，不调用 DeleteObject。迁移必须以实际服务版本验证条件写支持；客户端无法修复服务端忽略条件请求的问题。

## 操作步骤

```sh
# Go 1.26+，go.mod 选择 go1.26.10
go build -o bin/migration .
cp config.example.yaml config.yaml
# 编辑配置，为任务创建独立状态目录，并在外部冻结源写入/删除
./bin/migration list -c config.yaml
./bin/migration run -c config.yaml --source-frozen --bucket photos --rate-limit 20M
./bin/migration status -c config.yaml
./bin/migration diff -c config.yaml
```

配置完整说明见 [README](../README.md)。bucket 为空迁移全部源桶；未知字段会报错，避免拼错 bucket 后静默扩大范围。CLI > 环境变量 > YAML > 默认值。跨不可信网络使用 HTTPS；配置文件权限建议 0600。

## 恢复和升级

`scan` 完整扫描到 SQLite；失败扫描会使上一代完成凭证失效。`migrate --source-frozen` 必须使用已经扫描完成的清单，不会新建空库后宣告成功。`run --source-frozen` 先扫描再迁移。

每个状态库绑定源/目标端点与桶。不同任务使用不同目录或文件名，全桶模式也保留自定义文件名，如 job-a.db 派生 job-a-photos.db。旧版无端点身份且已有处理记录的 DB 不能自动接管；使用新目录重新扫描，程序会读回已有目标核对内容，不需要删除目标数据。

同一 DB 只允许一个写入进程。status 只读，可与迁移并行；缺库/坏库会报错。运行期间不要手工删除 DB、WAL、SHM 或 .lock 文件，也不要复制一个仍在变化的 DB 当成可靠备份。

源同 key 发生变化后重扫会重新验证，不会保持旧 done。目标有不同内容时记录 conflict，不会更新覆盖。这不是双向同步或持续同步工具。

## 校验与退出状态

迁移通过 If-Match/VersionId 固定源读取，验证清单身份、分片范围和长度。目标提交后完整读回做 SHA-256 校验；已有同大小对象也读取两端比较。不能比较或缺少稳定 ETag 时失败，不会退化到只验大小。

`diff` 验证两端桶、源清单中的 key、大小、完整 SHA-256 和保留的元数据。`diff --extra` 另外显示目标独有 key；目标允许有新业务对象，因此 extra 不独自令验收失败。

传输失败、取消、状态库错误、扫描不完整、diff 内容差异或验证错误都会非零退出。conflict 和明确源 NoSuchKey 的 skipped 需要人工核对。不能仅因 run 返回 0 就下线旧集群；还须确认冲突/跳过处置、最终 diff、冻结窗口和流量切换方案。

自动化场景可使用 `run --strict` 或 `migrate --strict`，状态库中存在待处理、失败、冲突或跳过对象时返回非零，包含之前运行留下的状态；`diff --strict` 也会检查并拒绝目标独有对象。严格模式不能代替冻结和最终内容验收。

`diff --issues-jsonl /path/to/new-file.jsonl` 可流式导出完整差异，每行包含 bucket、key、kind 和 detail，已有文件不会被覆盖。目标独有 key 需同时指定 `--extra` 或 `--strict` 才会记录。任务出错或中断可能留下不完整文件，应结合命令结果判断。

`spool_max_bytes` 默认 1 GiB，限制一次迁移中并发临时文件的预留总量。单个对象或分片超过预算会失败，可增大预算或降低分片大小、阈值。该限制不覆盖其他进程、异常退出留下的文件或磁盘上的其他数据；应使用专用临时目录、监控可用空间，并在确认任务已停止后清理遗留文件。

## 资源与清理

workers 控制对象并发，默认16；multipart_concurrency 控制单对象分片并发，默认4。分片落临时磁盘，单片5MiB到5GiB；磁盘峰值可能达到 workers×分片并发×分片大小，另有数据库和小对象开销。将 spool_dir 指向容量充足的磁盘。

rate_limit 限制 run/migrate 的所有源正文读取，包括分片完成前额外的完整源摘要读取。20M=20,000,000 B/s，20MiB=20×1024×1024 B/s，0=不限速。目标上传/校验读回和 diff 不受该限额限制。diff 会完整读取两端数据，需要安排业务负载窗口。

单对象正常迁移读取源1遍和目标1遍；分片正常迁移读取源约2遍和目标1遍。可靠校验增加读流量，不能套用旧版仅 HEAD 对比的成本估计。

普通失败会取消同对象其他分片并尝试 AbortMultipartUpload。SIGKILL 或主机断电无法执行 abort，应配置服务端未完成分片清理生命周期。恢复是对象级重试，不保证复用已经上传的分片。

## 能力范围与测试

保留当前对象内容、常见内容响应头、用户 metadata。不复制版本历史、删除标记、对象 tags、ACL、存储等级、源 SSE 配置、Object Lock/保留期、桶策略和生命周期。依赖这些语义的业务需要额外方案。

```sh
go test ./...
go test -race ./...
go vet ./...
python3 scripts/audit-local-rustfs.py \
  --rustfs-binary /absolute/path/rustfs --expect-version 1.0.4
```

将 `/absolute/path/rustfs` 替换为待测 RustFS 二进制的绝对路径。最后一条命令先运行这个文件的 `--version`，要求版本与 `1.0.4` 精确一致；不一致时不启动任何实例，也不会退回 PATH 中已有的其他版本。验证后使用同一二进制创建两个独立回环实例及临时数据，结束后清理。

启动器将实际二进制路径、版本输出和 SHA-256 保存到 `audit-results/rustfs-1.0.4/rustfs-binary.json`，同目录保存节点日志；可用 `--output-dir` 改变证据目录。独立的 `real_s3` 测试包含完整内容验收，以及真实分片上传取消、Abort 清理、重开 SQLite 后恢复等场景。测试覆盖范围不等于测试已经通过，`1.0.4` 的结论必须以实际执行结果为准。

本机旧 RustFS `1.0.0-alpha.61` 的分片兼容失败仅作为该版本的历史证据保留，不能解释为 `1.0.4` 的通过或失败。请对拟上线版本验证，不通过时不能关闭完整性校验绕过。具体结果见 [修复验证记录](FIXES-2026-10-29.md)。
