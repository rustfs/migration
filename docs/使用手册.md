# migration 中文使用手册

安全的单向 S3 迁移工具：从来源集群复制对象到目标集群。适用于 RustFS、MinIO 以及其它 S3 兼容存储。

**永不覆盖目标上已有对象。永不删除任何一侧的数据。中断后续跑即可。**

---

## 1. 你只需要记住两条命令

```bash
cp config.example.yaml config.yaml          # 填写来源 / 目标地址和密钥
./bin/migration run  -c config.yaml         # 扫描 + 复制
./bin/migration diff -c config.yaml         # 核对来源是否都到了目标
```

并发不够或代理吃不消时，加上并发开关。要保护生产带宽时，再加每秒读取上限（也可以写在 YAML 里）：

```bash
./bin/migration run -c config.yaml --workers 32 --multipart-concurrency 4 --rate-limit 20M
```

`config.yaml` 里 `bucket:` 留空，就会迁移来源上的**每一个桶**。只迁一个桶时写成 `bucket: photos`，或命令行加 `--bucket photos`。

查看全部帮助（中英双语）：

```bash
./bin/migration --help
./bin/migration run --help
./bin/migration diff --help
```

## 2. 安装、本机编译与 Linux 发行二进制

需要 Go 1.22+。纯 Go SQLite，**不需要 CGO**。`CGO_ENABLED=0` 打出来的是静态链接 ELF，目标机不需要 Go 或 C 编译器。

```bash
git clone https://github.com/rustfs/migration.git
cd migration
make build
# 等价于：CGO_ENABLED=0 go build -o bin/migration .
```

交叉编译 Linux x86_64（`GOARCH=amd64`）和 Linux arm64。CGO 关闭，所以在 amd64 上编 arm64 不需要 C 交叉编译器：

```bash
make build-linux-amd64    # bin/migration-linux-amd64
make build-linux-arm64    # bin/migration-linux-arm64
make build-linux           # 两个都编
```

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o bin/migration-linux-amd64 .
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o bin/migration-linux-arm64 .
file bin/migration-linux-amd64 bin/migration-linux-arm64
sha256sum bin/migration-linux-amd64 bin/migration-linux-arm64
```

`bin/` 不进 git。`file` 应看到 `statically linked`，架构分别是 `x86-64` 和 `ARM aarch64`。

## 3. 配置

```yaml
old:                              # 来源（只读）
  endpoint: "http://10.0.0.1:9000"
  access_key: "OLD_AK"
  secret_key: "OLD_SK"
  region: "us-east-1"

new:                              # 目标（读 + 写，需要能 CreateBucket）
  endpoint: "http://haproxy.new.local:9000"
  access_key: "NEW_AK"
  secret_key: "NEW_SK"
  region: "us-east-1"

bucket: ""                        # 空 = 全部桶
db_path: "./migration.db"
conflict_log: "./conflict.log"
spool_dir: ""                     # 小对象临时目录，默认跟 db 同目录

workers: 16                       # 对象并发。0 或省略 = 16
multipart_threshold: 52428800     # ≥ 50MiB 走分片上传。0 或省略 = 50MiB
multipart_part_size: 16777216     # 16 MiB。0 或省略 = 16MiB。非末片必须 ≥ 5 MiB（5242880）；更小会在加载配置时失败
multipart_concurrency: 4          # 单个大对象的分片并发。0 或省略 = 4
rate_limit: 0                     # 源读取合计上限。0 或省略 = 不限速
```

`rate_limit` 就是 MB/s 这一层，单位规则和谁受它限制见 [§3.1](#31-谁覆盖谁) 和 [§9.3](#93-带宽限速)。在途请求数由 `workers` 和 `multipart_concurrency` 决定，见 [§9.1](#91-并发)。

地址一律按 **path-style** 访问（自建 RustFS / MinIO 的常见方式）。

### 3.1 谁覆盖谁

优先级从高到低：

1. 命令行 `--workers`、`--multipart-concurrency`、`--rate-limit`、`--bucket`
2. 环境变量
3. YAML
4. 内置默认值（`workers=16`，`multipart_concurrency=4`，分片阈值 50MiB，分片大小 16MiB，`rate_limit` 不限速）

环境变量：

`OLD_ENDPOINT` `OLD_AK` `OLD_SK` `OLD_REGION`  
`NEW_ENDPOINT` `NEW_AK` `NEW_SK` `NEW_REGION` `REGION`  
`BUCKET` `DB_PATH` `CONFLICT_LOG` `SPOOL_DIR`  
`WORKERS` `MULTIPART_CONCURRENCY` `RATE_LIMIT`

并发数字的写法：

| 写法 | 结果 |
| --- | --- |
| YAML 省略，或写成 `0` | 用默认值 |
| YAML 写成负数，或分片阈值 / 分片大小为负数 | 启动即报错 |
| 环境变量 `WORKERS` / `MULTIPART_CONCURRENCY` 未设置 | 沿用 YAML |
| 环境变量设为 `0`、负数或非整数 | 报错，不会悄悄退回默认值 |
| 命令行没写这两个 flag | 沿用环境变量或 YAML |
| 命令行写了 `--workers 0` 或负数 | 报错 |

例子：YAML 里 `workers: 8`，环境变量 `WORKERS=32`，命令行 `--workers 4`，实际使用 **4**。

`rate_limit` 的 `0` 在每一层都表示不限速，包括命令行 `--rate-limit 0` 和 `RATE_LIMIT=0`。这和 `workers` 不同：`workers` 在 YAML 里写 `0` 才表示默认 16，写在命令行或环境变量里会报错。

带宽的写法（大小写不敏感）：

| 写法 | 含义 | 字节/秒 |
| --- | --- | --- |
| `20M`、`20MB` | 十进制兆字节，20×1000×1000 | 20000000 |
| `30M` | 十进制，30×1000×1000 | 30000000 |
| `50M`、`50MB` | 十进制，50×1000×1000 | 50000000 |
| `20Mi`、`20MiB` | 二进制兆字节，20×1024×1024 | 20971520 |
| `2K`、`2KB` | 十进制，2×1000 | 2000 |
| `2Ki`、`2KiB` | 二进制，2×1024 | 2048 |
| `1G`、`1GB` | 十进制，1000³ | 1000000000 |
| `1Gi`、`1GiB` | 二进制，1024³ | 1073741824 |
| 裸数字，如 `1048576` | 字节/秒 | 1048576 |
| `0`、`0M`，或整项省略 | 不限速 | — |

`M` 不是 `Mi`。口语里的「20 兆」如果按 1024 算，要写成 `20Mi` 或 `20MiB`，不要写成 `20M`。`20M` 比 `20MiB` 少大约 5%（20000000 对 20971520）。

## 4. 命令说明

| 命令 | 作用 | 是否写目标 | 用到的并发 |
| --- | --- | --- | --- |
| `migration list -c config.yaml` | 列出源集群全部桶 | 否 | 无 |
| `migration run -c config.yaml` | **推荐**：先扫描再复制 | 是（但不覆盖） | 复制阶段用 `workers`、`multipart_concurrency` 和 `rate_limit`；扫描阶段不用 |
| `migration scan -c config.yaml` | 只扫描，写入本地 SQLite | 否 | 无。始终单线程，不限速 |
| `migration migrate -c config.yaml` | 只复制 SQLite 里 pending/failed 的对象 | 是 | `workers` + `multipart_concurrency` + `rate_limit` |
| `migration status -c config.yaml` | 看本地进度，不访问 S3 | 否 | 无 |
| `migration diff -c config.yaml` | 按源清单对目标做 HEAD，查缺失和不一致 | 否 | `workers`（并行 HEAD）。不限速 |
| `migration diff --extra -c config.yaml` | 同上，并列出**仅目标上有**的 key | 否 | `workers` |

通用参数：

- `-c, --config` 配置文件，默认 `config.yaml`
- `--bucket NAME` 覆盖 YAML 里的桶名
- `--workers N` 对象并发。`run` / `migrate` 同时复制 N 个对象；`diff` 同时 HEAD N 个对象。必须 `>= 1`
- `--multipart-concurrency N` 单个大对象内部同时上传的分片数。必须 `>= 1`。`diff` / `scan` / `list` 不使用它
- `--rate-limit SIZE` 所有复制 worker 从源读取的合计上限，例如 `--rate-limit 20M`。`0` 表示不限速。`scan` / `diff` / `list` 不使用它
- `--help` 中英双语帮助
- `--version` 版本号

`list` 忽略桶筛选，总是列出源上全部桶。`--bucket` 里若有空格或 `/`，加载时仍会失败。

`scan` 结束日志里的对象数是这次 List 看到的个数，包含已经 `done` 的 key，不是「新发现多少」。真正待拷的数量看 `status` 的 `PENDING` 和 `FAILED`。

`run` 退出码 0 只说明没有致命错误。单个对象失败记成 `failed`，命令本身仍然成功。结束前看 `status`，再用 `diff`。

## 5. 推荐操作流程

### 5.1 全量迁移（最常用）

```bash
./bin/migration list -c config.yaml                 # 确认能连上来源
./bin/migration run  -c config.yaml --workers 16 --rate-limit 20M   # 扫描并复制，源读取合计不超过 20MB/s
./bin/migration status -c config.yaml               # 看进度
./bin/migration diff -c config.yaml --workers 32    # 确认源上的对象都在目标上
```

`run` 对每个桶会：

1. 检查源桶存在（`HeadBucket`）
2. 目标没有该桶则创建（已有则不动）
3. `ListObjectsV2` 全量扫描，写入 SQLite（单线程）
4. 启动 `workers` 个复制协程。每个对象先 `HeadObject` 目标。不存在则 GET 来源、PUT 目标，所有 GET 正文共用 `rate_limit`。已存在且与清单一致（大小相同；两边都有 ETag 且都不是分片 ETag `xxx-N` 时，ETag 也相同）记为 `done`，不再上传。已存在但不一致则写入冲突日志，不覆盖
5. 大对象（size ≥ `multipart_threshold`）在该对象内部再用 `multipart_concurrency` 个分片并行上传，这些分片同样计入同一个限额
6. 校验大小；单分片对象再比 ETag

### 5.2 只迁一个桶

```bash
./bin/migration run -c config.yaml --bucket photos --workers 8 --multipart-concurrency 8 --rate-limit 30M
```

### 5.3 增量补拷（源上后来新写入的对象）

S3 的 List 接口**不能**按修改时间在服务端过滤。正确做法是再扫一遍全量清单：

```bash
./bin/migration scan    -c config.yaml   # 新 key 变成 pending；曾经 skipped 后又出现的也会重试
./bin/migration migrate -c config.yaml --workers 16
./bin/migration diff    -c config.yaml
```

或直接再跑一次 `run`（已 `done` / `conflict` 的行不会被覆盖重传）。

### 5.4 中断后续跑

第一次 `Ctrl-C` 或 `SIGTERM`：取消 worker 池，也取消正在等 `rate_limit` 额度的读取。还没开始的对象保持 `pending`；正在上传的分片会 `AbortMultipartUpload`。这次 Abort 用一个新的 30 秒上下文，主任务取消不会把它一起取消。Abort 只丢掉未完成的 upload id，不删除已提交对象。SQLite 里已经写完的状态会保留。再按一次强制退出，退出码 `130`，Abort 可能被掐断。

`kill -9` 来不及 Abort，也来不及删 `spool_dir` 里的 `migration-*` 临时文件。旧 upload id 不会被这次进程回收，下次复制会新建上传；未完成分片靠桶的生命周期清理。

若中断发生在目标 `PutObject` 已成功、SQLite 尚未写成 `done`，该行会停在 `failed`，但目标上已经有对象。下次 `migrate` 看到大小一致，且可比的 ETag 也一致时，记为 `done`，而不是 `conflict`。只有大小不同或可比 ETag 不同才算冲突，并且仍然不会覆盖。

取消（`context.Canceled`）、截止时间或 `request canceled` 记为 `failed`，下次直接 `migrate` 就会重试。错误文本里即使出现 `NotFound` 或 `StatusCode: 404`（分片 Abort 经常带 NoSuchUpload），也不记 `skipped`。`skipped` 只表示源请求完整结束，并确认对象已经不在。

```bash
./bin/migration migrate -c config.yaml    # 只重试 pending / failed
```

### 5.5 先盘点、再决定是否拷

```bash
./bin/migration scan   -c config.yaml
./bin/migration status -c config.yaml     # 看有多少对象、多大
# 确认后再
./bin/migration migrate -c config.yaml --workers 16
```

`status` 不访问 S3。全桶模式下它会找 `db_path` 旁边的 `migration-*.db`。

## 6. 状态机（每个对象一行）

| 状态 | 含义 | 再扫会刷新吗 |
| --- | --- | --- |
| `pending` | 待拷 | 会更新 size/etag |
| `failed` | 上次失败，`migrate` 会重试 | 会回到 pending |
| `skipped` | 源请求完整返回 404（对象已删）。取消或超时不是 skipped | **会**回到 pending（对象后来又出现时） |
| `done` | 已拷到目标并校验，或目标上已有与清单一致的对象 | 不会动 |
| `conflict` | 目标已有同名对象，且与清单不一致（大小或可比 ETag 不同），未覆盖 | 不会动 |

冲突行写入 `conflict.log`（TSV）：

```
<object-key>	<source-LastModified>	<target-LastModified>
```

单桶模式使用你配置的 `db_path` / `conflict_log`。全桶模式自动变成：

- `migration-<桶名>.db`
- `conflict-<桶名>.log`

不要混用这两种模式。YAML 写了桶名、设置了 `BUCKET`，或带了 `--bucket`，状态就写在 `db_path` 本身（默认 `./migration.db`），**不是** `migration-<桶>.db`。先用 `--bucket photos` 跑过，再改成全桶，`status` 可能把 `photos` 打成两行，数字还不一样。选定一种之后保持不变。

指定桶时，`status` 会打开 `db_path`。文件不存在会被 SQLite 建成空库（`TOTAL=0`）。空库只表示文件刚被创建，不表示已经扫描过。全桶模式找不到 `migration-*.db` 时会提示先 `run` 或 `scan`。

每个库绑定一个桶。拿别的桶的库来用，会报 `db_path is bound to bucket "X" but config requests "Y"`。进程旁边会有 `-wal` / `-shm`。不要对同一个库再起一个进程。

SQLite 以 WAL 打开。进程内只用一条数据库连接，避免把 `workers` 开大以后出现 `database is locked`。对象的字节流不经过这条连接，复制本身仍然并行。

`migrate` 每 10 秒打一行本进程计数。`copied` / `bytes` 是这次被记成 `done` 的对象个数和大小，包含「目标已经一致、没有重新 GET」的对象。这不是网卡吞吐，也不是 `rate_limit` 扣掉的字节。限额是否生效，看启动日志，例如 `rate_limit=20MB/s`（YAML 或 `--rate-limit 20M`）或 `rate_limit=50MB/s`（`50M` = 50000000 字节/秒）。`0` 会显示成 `unlimited`。

查失败原因：

```bash
sqlite3 migration-photos.db \
  "SELECT key, attempts, last_error FROM objects WHERE status='failed' LIMIT 20;"
```

## 7. diff 怎么读

```text
=== diff photos ===
ok=1000  missing=2  size_mismatch=0  etag_mismatch=1  extra_on_target=0
一致=1000  缺失=2  大小不一致=0  ETag不一致=1  仅目标有=0
  missing  a.txt  not on target
  etag     b.txt  src=abc dst=def
```

- **missing**：源有、目标没有 → 再跑 `migrate` 或 `run`
- **size / etag**：两边同名但内容对不上（目标可能被别的写入改过；本工具不会覆盖）
- **extra_on_target**（需 `--extra`）：只在目标上，通常是业务已经写到新集群，**不算失败**

有 missing / size / etag 时退出码为 `1`。明细最多打印 50 条，然后是 `... and N more issues / 还有 N 条未打印`，汇总数字是全的。

`--workers` 在 diff 里只控制并行 HEAD。diff 不读取 `multipart_concurrency`，也不吃 `rate_limit`，不会上传或删除，也不会创建目标桶。目标桶不存在时，源上的 key 都会是 missing。

`diff` 不读迁移用的 SQLite。临时清单在操作系统临时目录：`migration-diff-<桶>-<pid>.db`，命令结束删除主文件。桶很大而 `/tmp` 是内存盘时，这个库会占内存。它和 `spool_dir` 不是同一个目录。

## 8. 安全保证

| 保证 | 做法 |
| --- | --- |
| 永不覆盖目标对象 | 写之前强制 `HeadObject` |
| 永不删除 | 代码里没有 `DeleteObject`（分片失败只 `AbortMultipartUpload`） |
| 不走错桶 | `HeadBucket` + 每页 Name 校验 + SQLite 绑定桶名 |
| 源中途被删 | 只有完整返回的源 404 记 `skipped`；取消或超时记 `failed` |
| 崩溃可续 | 每对象状态在 SQLite WAL |
| 取消可续 | 第一次信号取消 worker；未完成的对象下次 `migrate` 继续 |
| 内存有上限 | 小对象落盘；大对象按分片读。等待队列最多约 2048 个对象描述，不会把全桶清单堆进内存 |
| 拷后校验 | 比 size；单 part 再比 ETag |

### 8.1 会保留的对象元数据

小对象从 `GetObject` 取属性，大对象先 `HeadObject` 来源，再交给 `CreateMultipartUpload`。两边都会写到目标：

- `Content-Type`
- `Cache-Control`
- `Content-Disposition`
- `Content-Encoding`
- `Content-Language`
- `Expires`
- 用户元数据 `x-amz-meta-*`

来源没有 `Content-Type` 时，工具不另造一个。这些 HEAD 不计入 `rate_limit`；计入限额的是随后读到的对象正文。

### 8.2 不会迁移的内容

- 历史版本、删除标记（只用 `ListObjectsV2` 的当前对象，没有 `ListObjectVersions`）
- Object Lock：保留期、Legal Hold
- 对象标签、ACL、Storage Class
- SSE-C / SSE-KMS 参数（不带客户密钥，也不指定 KMS key）。来源对象如果没有客户密钥就无法 GET，该行记 `failed`
- 桶策略、生命周期、CORS、复制规则、事件通知、静态网站、日志、默认加密
- 服务端 `CopyObject`（两个集群之间也不能用）

源对象若是 SSE，单分片 ETag 可能对不上内容 MD5。PUT 已经落盘之后校验失败，行先记 `failed`；下次 `migrate` 若看到不一致的单分片 ETag，会改记 `conflict` 并且不再覆盖。数据可能已经在目标上。可以把 `multipart_threshold` 调低，让更多对象只比大小。

## 9. 并发与带宽

### 9.1 并发

字节速率用 `rate_limit` / `--rate-limit`，见 [§9.3](#93-带宽限速)。并发决定在途请求数：

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `workers` | 同时在拷贝的对象数。`diff` 对目标做 HEAD 时也用这个并发。命令行 `--workers`，环境变量 `WORKERS` | 16 |
| `multipart_concurrency` | 单个大对象里并行上传的分片数（只在 `run` / `migrate` 的分片路径上）。命令行 `--multipart-concurrency`，环境变量 `MULTIPART_CONCURRENCY` | 4 |

`workers` 和 `multipart_concurrency` 是两层：

```text
workers = 4 个对象同时复制
  对象 A（小文件）  ── 1 个 GET + PUT
  对象 B（小文件）  ── 1 个 GET + PUT
  对象 C（大文件）  ── multipart_concurrency 个分片同时 GET + UploadPart
  对象 D（大文件）  ── 同上
```

峰值大约是 `workers × multipart_concurrency`。小对象每个只占一路；达到 `multipart_threshold` 的大对象会按分片把并发乘上去。默认 `16 × 4` 很容易打满网卡、源或目标集群，以及前面 HAProxy 的 `maxconn`。

希望少影响生产时，用 `--rate-limit 20M`（或 `30M`、`50M`）直接封顶源读取。在途请求仍然太多时，再把 `workers` 调小；大对象占满链路时，再把 `multipart_concurrency` 调小。改完看 `migration status` 的本地进度，并在机器上看网卡和集群负载（`status` 本身不访问 S3）。

```yaml
# 降负载的起点。先跑一小段，再按 status 和网卡调整。
workers: 2
multipart_concurrency: 2
```

| 场景 | 建议 |
| --- | --- |
| 海量小文件，链路有余量 | `workers` 16～64，`multipart_concurrency` 保持 4 |
| 大小文件混合 | `workers` 8～32，`multipart_concurrency` 4～8 |
| 主要是超大对象 | `workers` 2～8，`multipart_concurrency` 4～16 |
| 排查单个对象为什么失败 | `--workers 1`，变成串行，日志更好对 |
| 代理返回 503、大量超时、源盘 100% | 先减 `workers`。如果慢的是大文件，再减 `multipart_concurrency` |
| 扫描阶段想加速 | 做不到。`scan` 固定单线程，加大 `--workers` 不会让 List 变快 |
| 迁移时要给生产留带宽 | `--rate-limit 20M` 起步，观察源集群后再调到 `30M` 或 `50M`。业务低峰可以设 `0` 取消限额 |

链路有余量、想更快时反过来：小文件多就加大 `workers`；单个大文件就加大 `multipart_concurrency`，或减小 `multipart_part_size`（单位字节，默认 16 MiB，不能小于 5 MiB）。

`multipart_part_size` 必须 ≥ 5 MiB（5242880）。S3 / RustFS 规定除最后一片外每片至少 5 MiB，否则上传返回 `EntityTooSmall`。默认 16 MiB 已满足，不会改。配置写得更小则在加载时直接报错，不会把数值悄悄抬到 5 MiB。分片数超过 10000 时工具会自动加大 `part_size`，一般不用手改。

### 9.2 其它注意

- `/tmp` 若是内存盘，把 `spool_dir` 指到真实磁盘。每个正在复制的小对象占一个临时文件，最大约 `multipart_threshold`，个数随 `workers` 上升
- SQLite 单文件不要多进程同时写同一个 `db_path`
- 不要按「启动时间窗口」自己做增量，List API 做不到；请全量再扫

SQLite 存的是元数据（key/size/etag/状态），几千万行通常没问题。对象过亿时本工具用 keyset 分页拉 pending，内存仍然受控。多台机器同时迁同一批对象需要以后换独立数据库，当前版本是单机。

### 9.3 带宽限速

`rate_limit` 是**所有正在复制的 worker 共用**的每秒字节上限，包括同一个大对象里并行的分片。实现是一个令牌桶：从源读到的对象字节都从这同一个额度里扣。多个 S3 桶按顺序迁移，同一时刻只有一个桶在复制，所以这个数字就是整个进程从源拉对象数据的上限。

它统计的是源对象正文，不统计 List、HEAD 和冲突检查。因此：

- `run` 的扫描阶段不限速，复制阶段限速
- `migrate` 限速
- `scan`、`diff`、`list`、`status` 不限速

`20M` 表示每秒最多读 20000000 字节（十进制 MB）。`20MiB` 表示每秒 20971520 字节。生产上想少影响在线业务时，从 `20M` 开始，确认源延迟正常后再放到 `30M` 或 `50M`。设为 `0` 或从配置里删掉这一项，就是不限速。

上传不重复扣这个额度。小对象会先按限额从源读完，再写入目标，所以源侧的读取速度不超过配置值；目标侧在读完之后可能短时更快。迁移进程和业务如果走同一块网卡，写入仍会再占带宽，请把额度留出余量。

限速不改变安全模型。目标上已有且与清单一致的对象记 `done`，不再上传；不一致才记冲突，不覆盖。没有任何删除。第一次 Ctrl-C 会取消正在等待额度的读取，未完成的对象留在 SQLite，再次执行 `migrate` 即可继续。

YAML、环境变量和命令行示例（优先级：命令行 > 环境变量 > YAML）：

```yaml
rate_limit: 20M
```

```bash
RATE_LIMIT=30M ./bin/migration run -c config.yaml
./bin/migration migrate -c config.yaml --rate-limit 50M
./bin/migration run -c config.yaml --rate-limit 0          # 明确取消限额
```

## 10. 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 命令没有返回错误。对象级 `failed` 仍可能是 0。只迁一个桶时，复制阶段第一次 Ctrl-C 也会以 0 结束，没做完的对象留在 SQLite 里 |
| 1 | 配置错误、远端错误、某个桶失败，或 diff 发现缺口。扫描过程中按 Ctrl-C，或一次迁移多个桶时被中断，同样是 1 |
| 130 | 第二次 SIGINT / SIGTERM，强制退出 |

验收标准是 `status` 里 `PENDING=0` 且 `FAILED=0`，并且 `diff` 退出码 0。

## 11. 常见问题

| 现象 | 处理 |
| --- | --- |
| 想把速度限在大约 20 MB/s | `--rate-limit 20M`（十进制，20000000 字节/秒）。1024 进制写 `20MiB`。见 §9.3 |
| `old.endpoint is required` | 检查 YAML 或 `OLD_ENDPOINT` |
| `multipart_part_size must be >= 5242880` | 分片小于 5 MiB。改成 ≥ 5242880（默认 16 MiB）。工具不会自动抬高 |
| `workers must be >= 1` | 命令行、`WORKERS` 或 YAML 的 `workers` 不合法。YAML 的 `0` 才表示默认 16 |
| `multipart_concurrency must be >= 1` | 同上，针对分片并发 |
| `env WORKERS="…" is not an integer` | 环境变量里有空格或单位，改成纯数字。带宽要用 `RATE_LIMIT=20M`，不要把单位写进 `WORKERS` |
| `unknown size suffix` 或 `rate limit` | `rate_limit` / `RATE_LIMIT` / `--rate-limit` 的单位无法识别。十进制写 `20M`，1024 进制写 `20MiB` |
| 限速后源仍然很忙 | `20M` 只限制从源读出的对象字节。上传另算。共用网卡时把数字再调低，例如 `20M` 改成 `10M` |
| 扫描、diff 没有变慢 | 正常。限额只在复制对象正文时生效 |
| `head bucket "…" on source` | 桶不存在、地址错、或密钥没有读权限 |
| `head bucket "…" on target` | 目标 HEAD 失败且不是 404，不会去 CreateBucket |
| `create bucket … on target (need s3:CreateBucket)` | 目标密钥不能建桶。`diff` 不会建桶 |
| `read config … copy config.example.yaml first` | `-c` 路径错，或还没复制样例 |
| `list page bucket mismatch` | List 返回的桶名和请求不一致，为防走错桶直接失败 |
| 扫描很慢 | 正常，`scan` 是单线程。并发从 `migrate` / `run` 的复制阶段才开始 |
| 加大 workers 后 503 变多 | 减小 `workers`。大对象再减小 `multipart_concurrency`，让峰值 `workers × multipart_concurrency` 低于代理 `maxconn` |
| 大量 `etag mismatch` | 源端 SSE/压缩会改 ETag。上传可能已经在目标上，下一轮会变成 `conflict` 而不覆盖。可把 `multipart_threshold` 调低走分片（只校验 size），或人工抽查 |
| `size mismatch after put` / `size mismatch after multipart` | 校验失败，行是 `failed`。工具不会删掉已经写下的对象 |
| `run` 是 0，但 `diff` 还有 missing | 对象失败不会让 `run` 失败。看 `last_error`，再 `migrate` |
| `status` 是空的，但刚跑完全桶 | 全桶库是 `migration-<桶>.db`。`--bucket` 看的是 `db_path` |
| `x509` / `certificate` | 没有跳过 TLS 校验的开关。换成受信任证书，或经校验证书的代理 |
| `AccessDenied` / `SignatureDoesNotMatch` / `InvalidAccessKeyId` | AK/SK 和 endpoint 不配对，或环境变量盖住了 YAML |
| `RequestTimeTooSkewed` | 先对时 |
| `kill -9` 之后目标上有未完成分片 | 工具不回收旧 upload id。靠桶生命周期清理 |
| `db_path is bound to bucket "X"` | 一个 db 只绑定一个桶，换路径 |
| `database is locked` | 不要对同一 db 起两个进程 |
| 磁盘被写满 | 检查 `spool_dir`。workers 大时临时文件更多 |
| Ctrl-C 退不出 | 等当前请求结束，或再按一次 |
| diff 还有 missing | 再 `migration migrate`；看 `failed` 行的 `last_error` |

## 12. 和生产架构的关系

典型场景：旧集群只读历史数据，新集群承接全部写入；应用双读。本工具把旧集群上「目标还没有的 key」补过去，**不会**把新集群上更新的对象打回旧内容。

因此：同名但与清单不一致才是冲突，请看 `conflict.log`，不要改成覆盖模式。与清单大小（以及可比 ETag）一致的目标对象会记为 `done`。`rate_limit` 只让读取变慢，不改变这条规则。

在 RustFS 1.0.4 上建议按这个顺序自己看一遍，再放量：

1. `list` 能列出来源的桶
2. 对一个小桶 `run --rate-limit 20M`（或你在 Mac 上用过的 `50M`）。启动日志应出现 `rate_limit=20MB/s` 或 `rate_limit=50MB/s`，而不是 `unlimited`
3. 中途 Ctrl-C 一次。被打断的行应是 `pending` 或 `failed`，不是 `skipped`。再 `migrate` 到 `FAILED=0`
4. 立刻再 `run` 一遍。已 `done` 的对象不应重传。`diff` 退出码 0
5. 在目标上预先放一个同名但大小不同（或单分片 ETag 不同）的对象，再迁移：该 key 为 `conflict`，目标内容不变，`conflict.log` 多一行
