# migration

[English](README.md) | [简体中文](README_ZH.md) | [Deutsch](README_DE.md) | [Español](README_ES.md) | [Français](README_FR.md) | [日本語](README_JA.md) | [한국어](README_KO.md) | [Português](README_PT.md) | **Русский**

Утилита `migration` копирует текущие версии объектов из одного S3-совместимого кластера в другой. Например, с её помощью можно перенести архив из RustFS или MinIO, когда приложение уже пишет в новый кластер. В конфигурации `old` обозначает источник, а `new` — приёмник. Имя бакета указывается в пути запроса к S3.

Утилита копирует недостающие объекты, записывает конфликты в `conflict.log` и сохраняет ход переноса в локальной базе SQLite. Объекты не удаляются. Приёмник должен учитывать условие `If-None-Match: *` для `PutObject` и `CompleteMultipartUpload`. Тогда объект, созданный приложением после проверки ключа, также будет сохранён.

Вместе с содержимым объекта переносятся заголовки `Content-Type`, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`, `Expires` и пользовательские метаданные `x-amz-meta-*`. Миграция не затрагивает историю версий, маркеры удаления, Object Lock, политики бакетов и правила жизненного цикла.

## Быстрый старт

Для сборки из исходного кода нужен Go 1.22 или новее. Скопировав шаблон, укажите адреса и учётные данные обоих кластеров в `config.yaml`.

```bash
git clone https://github.com/rustfs/migration.git
cd migration
CGO_ENABLED=0 go build -o bin/migration .
# или: make build
cp config.example.yaml config.yaml   # endpoint и ключи источника и цели
```

```bash
./bin/migration list   -c config.yaml
./bin/migration run    -c config.yaml --workers 16 --rate-limit 20M
./bin/migration status -c config.yaml
./bin/migration diff   -c config.yaml
```

Пустой `bucket:` переносит каждый бакет источника. `bucket: photos` или `--bucket photos` фиксирует один.

Флаг `--bucket ""` выбирает все бакеты источника, даже если один бакет указан в YAML или в переменной `BUCKET`.

Параметр `--rate-limit 20M` ограничивает суммарную скорость чтения из источника до 20 000 000 байт/с. Другие единицы описаны в разделе [Ограничение скорости](#rate-limit).

## Установка

Откройте успешную сборку в [Build packages](https://github.com/rustfs/migration/actions/workflows/packages.yml) и выберите свою платформу в разделе **Artifacts**. Распакуйте загруженный файл, сверьте контрольную сумму архива с приложенной суммой SHA-256, затем извлеките содержимое архива. Для Linux (amd64 и arm64) доступны пакеты `.tar.gz`, для Windows (amd64) — архив `.zip` с программой `migration.exe`.

```bash
./migration --version
```

```powershell
.\migration.exe --version
```

Защитите `config.yaml` (`chmod 600` — разумное значение по умолчанию). Процесс пишет в журнал endpoint и ключи объектов. Учётные данные он не пишет.

## Конфигурация

```bash
cp config.example.yaml config.yaml
```

Задайте для каждого кластера адрес HTTP или HTTPS и укажите учётные данные в отдельных полях. URL не должен содержать учётных данных, строки запроса или фрагмента. Для создания бакета на приёмнике требуется разрешение `s3:CreateBucket`.

```yaml
old:                              # источник, только чтение
  endpoint: "http://10.0.0.1:9000"
  access_key: "OLD_AK"
  secret_key: "OLD_SK"
  region: "us-east-1"
new:                              # цель, чтение и запись
  endpoint: "http://haproxy.new.local:9000"
  access_key: "NEW_AK"
  secret_key: "NEW_SK"
  region: "us-east-1"

bucket: ""                        # пусто = каждый бакет источника
db_path: "./migration.db"
conflict_log: "./conflict.log"
spool_dir: ""                     # временные файлы малых объектов; по умолчанию каталог базы

workers: 16                       # объектов одновременно; 0 или пропуск = 16
multipart_threshold: 52428800     # >= 50 MiB идёт multipart-загрузка
multipart_part_size: 16777216     # 16 MiB; должно быть >= 5 MiB (5242880)
multipart_concurrency: 4          # части одного большого объекта; 0 или пропуск = 4
rate_limit: 0                     # общий потолок чтения с источника; 0 или пропуск = без ограничения
```

`list` и `scan` нуждаются в endpoint и ключах источника. `run`, `migrate` и `diff` нуждаются в обеих сторонах.

### Приоритет

Побеждает более высокий приоритет:

1. CLI: `--bucket`, `--workers`, `--multipart-concurrency`, `--rate-limit`
2. Переменные окружения
3. YAML
4. Встроенные значения по умолчанию

| Параметр | Значение по умолчанию, если пропущен |
| --- | --- |
| `workers` | 16 |
| `multipart_concurrency` | 4 |
| `multipart_threshold` | 50 MiB (52428800) |
| `multipart_part_size` | 16 MiB (16777216) |
| `rate_limit` | без ограничения |
| `db_path` | `./migration.db` |
| `conflict_log` | `./conflict.log` |
| `spool_dir` | каталог `db_path` |
| `region` | `us-east-1` |

Пример: YAML `workers: 8`, окружение `WORKERS=32` и `--workers 4` вместе дают **4**.

### Что означает ноль

`0` означает разное в разных полях.

| Поле | YAML `0` или пропуск | Окружение `0` | CLI `0` |
| --- | --- | --- | --- |
| `workers` | по умолчанию 16 | ошибка | ошибка (`--workers 0`) |
| `multipart_concurrency` | по умолчанию 4 | ошибка | ошибка |
| `multipart_threshold` | по умолчанию 50 MiB | нет переменной | нет флага |
| `multipart_part_size` | по умолчанию 16 MiB | нет переменной | нет флага |
| `rate_limit` | без ограничения | без ограничения (`RATE_LIMIT=0`) | без ограничения (`--rate-limit 0`) |

Отрицательная параллельность или размер останавливают запуск. `WORKERS` и `MULTIPART_CONCURRENCY` должны быть простыми целыми. Суффиксы размера ставятся только в `RATE_LIMIT`: `RATE_LIMIT=20M` допустимо, `WORKERS=20M` — нет.

Допустимое значение `multipart_part_size` — от 5 МиБ до 5 ГиБ, по умолчанию 16 МиБ. Объекты размером более 5 ГиБ всегда передаются по частям. Чтобы уложиться в 10 000 частей, утилита при необходимости увеличивает их размер. Если для этого потребовались бы части больше 5 ГиБ, перенос завершается ошибкой.

Имя бакета не должно содержать пробелов или `/`.

### Переменные окружения

Заданная переменная перекрывает YAML. Незаданная переменная оставляет файл как есть.

| Переменная | Перекрывает |
| --- | --- |
| `OLD_ENDPOINT` `OLD_AK` `OLD_SK` `OLD_REGION` | endpoint источника |
| `NEW_ENDPOINT` `NEW_AK` `NEW_SK` `NEW_REGION` | endpoint цели |
| `REGION` | ту сторону, у которой регион всё ещё пуст после специальных переменных |
| `BUCKET` | `bucket` |
| `DB_PATH` `CONFLICT_LOG` `SPOOL_DIR` | локальные пути |
| `WORKERS` `MULTIPART_CONCURRENCY` | параллельность (целое ≥ 1) |
| `RATE_LIMIT` | общий потолок чтения с источника (`20M`, `20MiB`, `0`, …) |

## Команды

```bash
./bin/migration --help
./bin/migration run --help
./bin/migration diff --help
```

| Команда | Что делает | Пишет на цель | Параллельность и потолок |
| --- | --- | --- | --- |
| `migration list -c config.yaml` | Перечисляет все бакеты источника | Нет | Нет |
| `migration run -c config.yaml` | **Рекомендуется.** Инвентаризация, затем копирование | Да, без перезаписи | Инвентаризация однопоточная. Копирование использует `workers`, `multipart_concurrency` и `rate_limit` |
| `migration scan -c config.yaml` | Инвентарь источника в SQLite | Нет | Один поток. Без ограничения скорости |
| `migration migrate -c config.yaml` | Копирует только строки SQLite в `pending` или `failed` | Да, без перезаписи | `workers`, `multipart_concurrency` и `rate_limit` |
| `migration status -c config.yaml` | Печатает локальные счётчики | Нет | Нет. Без вызовов S3 |
| `migration diff -c config.yaml` | Перечисляет источник и делает `HEAD` каждого ключа на цели | Нет | `workers` для параллельных HEAD. Без ограничения скорости |
| `migration diff --extra -c config.yaml` | То же, плюс ключи, которые есть только на цели | Нет | `workers` |

Общие флаги всех команд:

| Флаг | Смысл |
| --- | --- |
| `-c`, `--config` | Файл конфигурации. По умолчанию `config.yaml` |
| `--bucket NAME` | Фиксирует один бакет. Перекрывает YAML и `BUCKET` |
| `--workers N` | Сколько объектов копируется сразу в `run` / `migrate` и сколько параллельных HEAD в `diff`. Должно быть ≥ 1 |
| `--multipart-concurrency N` | Сколько частей одного большого объекта загружается сразу. Должно быть ≥ 1. `list`, `scan`, `status` и `diff` его игнорируют |
| `--rate-limit SIZE` | Общий потолок чтения тел объектов в `run` / `migrate`. `0` — без ограничения |
| `--version` | Печатает версию |
| `--help` | Двуязычная справка |

`diff` также принимает `--extra`.

`status` печатает `BUCKET`, `TOTAL`, `PENDING`, `DONE`, `CONFLICT`, `SKIPPED` и `FAILED`. Без зафиксированного бакета читает `migration-*.db` рядом с `db_path` и саму настроенную базу, если этот файл уже привязан к бакету. Если ничего ещё нет, сообщает об этом и завершается с кодом 0. Сначала выполните `scan` или `run`.

## Сценарии

### Перенести все бакеты

```bash
./bin/migration list   -c config.yaml
./bin/migration run    -c config.yaml --workers 16 --rate-limit 20M
./bin/migration status -c config.yaml
./bin/migration diff   -c config.yaml --workers 32
```

Для каждого бакета `run` делает следующее:

1. `HeadBucket` на источнике.
2. `ListObjectsV2` источника в SQLite. Этот шаг однопоточный.
3. Создаёт бакет на цели, если его нет. Существующий бакет не изменяется.
4. Одновременно копируется до `workers` объектов. Если после первого HEAD приложение создаст тот же ключ, условная запись сохранит данные приложения. Утилита проверит ключ ещё раз и запишет `done` или `conflict`.
5. Объекты размером от `multipart_threshold` передаются по частям, не более `multipart_concurrency` частей одного объекта одновременно. Ограничение скорости чтения общее для всех частей.
6. Проверяет размер на цели. Объект из одной части дополнительно проверяется по ETag, когда ETag сравнимы. См. [Состояние объектов](#resume-and-object-state).

Бакеты копируются по очереди, поэтому `rate_limit` — потолок всего процесса.

### Один бакет

```bash
./bin/migration run -c config.yaml \
  --bucket photos --workers 8 --multipart-concurrency 8 --rate-limit 30M
```

### Объекты, записанные на источнике позже

`ListObjectsV2` не умеет фильтровать по времени изменения на сервере. Догоняющий проход — это ещё одно полное перечисление. Новые ключи становятся `pending`. Строки `failed` или `skipped` возвращаются в `pending`, когда их снова перечисляют. `done` и `conflict` остаются как есть, поэтому второй проход их не пересылает и не перезаписывает цель.

```bash
./bin/migration scan    -c config.yaml
./bin/migration migrate -c config.yaml --workers 16
./bin/migration diff    -c config.yaml
```

Повторный `run` — те же два шага одной командой.

### Сначала инвентаризация

```bash
./bin/migration scan   -c config.yaml
./bin/migration status -c config.yaml    # счётчики объектов, без вызовов S3
./bin/migration migrate -c config.yaml --workers 16
```

## Параллельная передача

Число одновременно копируемых объектов задаёт `workers`. Для больших объектов параметр `multipart_concurrency` дополнительно ограничивает число частей одного объекта, передаваемых параллельно. При значениях по умолчанию (16 объектов, по четыре части) один кластер может получать до 64 запросов одновременно. При настройке учитывайте возможности дисков и прокси, а также объём свободной памяти.

`scan` игнорирует `workers` и `rate_limit`. Перечисление идёт страница за страницей: каждой странице нужен continuation token предыдущей, а строки попадают в один файл SQLite. Медленный scan не ускоряется через `--workers`. `list`, `diff` и `status` не читают тела объектов, поэтому потолок байт на них не действует. `diff` использует `--workers` для HEAD.

```text
workers = 4 объекта сразу
  объект A (малый)  ── один GET + PUT
  объект B (малый)  ── один GET + PUT
  объект C (большой)  ── multipart_concurrency GET по диапазону + UploadPart
  объект D (большой)  ── то же
```

Каждая передаваемая часть помещается в оперативную память. Очередь заданий вмещает не более 2048 описаний объектов. HTTP-клиент повторно использует соединения и может держать до 1024 незанятых соединений на каждый узел.

Отправные точки:

| Нагрузка | Предложение |
| --- | --- |
| Много малых объектов (килобайты — несколько мегабайт), канал свободен | `workers` 16–64, `multipart_concurrency` оставить 4 |
| Смешанные размеры | `workers` 8–32, `multipart_concurrency` 4–8 |
| Немного очень больших объектов | `workers` 2–8, `multipart_concurrency` 4–16 |
| Один объект падает, и журнал трудно читать | `--workers 1` |
| Прокси отвечает 503, таймауты или диск источника полон | Сначала снизить `workers`. Если медленные объекты большие, снизить и `multipart_concurrency` |
| Оставить полосу продакшену | `--rate-limit 20M`, затем `30M` или `50M`, когда источник выглядит здоровым. `0` снимает потолок |
| Быстрее на малых объектах | Поднять `workers` |
| Быстрее на одном большом объекте | Поднять `multipart_concurrency` или снизить `multipart_part_size` (байты, минимум 5 MiB) |

Во время копирования примерно каждые 10 секунд пишется строка прогресса: processed, copied, conflicts, skipped, failed и bytes.

У каждого малого объекта в полёте есть один временный файл в `spool_dir`, примерно до `multipart_threshold` байт, потому что `PutObject` нуждается в теле, по которому можно сделать seek. Если `/tmp` — диск в памяти, направьте `spool_dir` на настоящий диск. Больше worker — больше таких файлов одновременно.

Один процесс на файл базы. SQLite открывается в режиме WAL с одним соединением внутри процесса, поэтому обновления состояния идут последовательно, а байты объектов остаются в пуле worker. Второй процесс на том же файле по-прежнему сообщает `database is locked`.

<a id="rate-limit"></a>

## Ограничение скорости

`rate_limit` ограничивает суммарную скорость чтения из источника для всех объектов и их частей. Запросы списков и заголовков, а также загрузка на приёмник в этот лимит не входят.

Небольшие объекты сначала записываются на локальный диск, а затем отправляются на приёмник. Если чтение и отправка используют один сетевой интерфейс, при настройке ограничения скорости оставьте часть полосы для отправки.

### Единицы

Суффиксы не зависят от регистра. Завершающий `/s` принимается и игнорируется. Голое число — байты в секунду. `1.5M` — это 1 500 000 байт/с.

| Записано как | Байт в секунду |
| --- | --- |
| `20M`, `20MB` | 20×1000×1000 = 20000000 |
| `30M` | 30000000 |
| `50M`, `50MB` | 50000000 |
| `20Mi`, `20MiB` | 20×1024×1024 = 20971520 |
| `2K`, `2KB` | 2000 |
| `2Ki`, `2KiB` | 2048 |
| `1G`, `1GB` | 1000000000 |
| `1Gi`, `1GiB` | 1073741824 |
| `1T`, `1TB` / `1Ti`, `1TiB` | 1000⁴ / 1024⁴ |
| `1048576` | 1048576 |
| `0`, `0M` или пропуск | без ограничения |

`M` — десятичное. `Mi` — двоичное. `20M` примерно на 5 % ниже `20MiB` (20000000 против 20971520). Отрицательное значение или неизвестный суффикс останавливают запуск.

```yaml
rate_limit: 20M
```

```bash
RATE_LIMIT=30M ./bin/migration run -c config.yaml
./bin/migration migrate -c config.yaml --rate-limit 50M
./bin/migration run -c config.yaml --rate-limit 0    # без ограничения, намеренно
```

<a id="resume-and-object-state"></a>

## Возобновление переноса и состояния объектов

Первый Ctrl-C или `SIGTERM` отменяет пул worker. Объекты, которые ещё не начаты, остаются `pending`. Идущая multipart-загрузка отменяется: освобождается только эта загрузка, зафиксированный объект не удаляется. Состояние, уже записанное в SQLite, сохраняется. Второй сигнал завершает процесс сразу с кодом 130.

Если ETag объекта в источнике изменится между сканированием и копированием, перенос этого объекта завершится ошибкой. Обновите опись командой `scan` и повторите `migrate` или снова выполните `run`.

Отменённый запрос, дедлайн и `request canceled` — это `failed`, даже если текст ошибки содержит `NotFound` или `StatusCode: 404`. Отмена multipart часто сообщает `NoSuchUpload`. Это не отсутствующий объект источника. `skipped` значит, что запрос к источнику завершился и объекта действительно уже не было.

```bash
./bin/migration migrate -c config.yaml
```

`migrate` повторяет только `pending` и `failed`.

| Состояние | Смысл | Последующий scan |
| --- | --- | --- |
| `pending` | Ждёт копирования | Обновляет размер и ETag |
| `failed` | Последняя попытка не удалась. `migrate` повторит её. Сообщение в `last_error` | Возвращает строку в `pending` |
| `skipped` | Запрос к источнику завершился с 404 / `NoSuchKey` | Возвращает в `pending`, если ключ снова перечислен |
| `done` | Скопирован и проверен, или цель уже совпадала с инвентарём | Без изменений |
| `conflict` | На цели есть ключ, и он не совпадает с инвентарём. Не перезаписан | Без изменений |

Если ключ уже существует, состояние `done` присваивается только при одинаковом размере и совпадении двух непустых ETag. В остальных случаях записывается `conflict`, а существующий объект сохраняется. У одинаковых данных могут быть разные ETag из-за разбиения на части. Если перенос прервался сразу после загрузки, проверьте такие конфликты вручную.

Каждый конфликт — одна строка TSV в журнале, метки времени RFC3339 UTC:

```text
<object-key>	<source-LastModified>	<target-LastModified>
```

Ключи с управляющими символами или двойной кавычкой в начале записываются как строковые литералы Go с экранированием.

Один настроенный бакет использует `db_path` и `conflict_log` как написано. Режим всех бакетов выводит соседние файлы:

- `migration-<bucket>.db`
- `conflict-<bucket>.log`

Для `migrate` нужна опись, созданная командой `scan` или `run`. База состояния привязана к бакету и адресам кластеров. Перед использованием базы от предыдущей версии проверьте, к каким кластерам она относится. Первое сканирование запишет адрес источника, а первый перенос — адрес приёмника. После сбоя или прерывания сканирования повторите `scan` или `run`, прежде чем запускать `migrate`. В старых базах нет отметки о завершении сканирования. Если полнота описи вызывает сомнения, создайте её заново командой `scan`.

## Проверка цели через diff

`diff` сверяет размеры и сопоставимые ETag, не скачивая объекты. Счётчик `size_only` показывает, сколько объектов из числа `ok` проверено только по размеру. С флагом `--extra` создаётся временный индекс для поиска ключей, которые есть только на приёмнике. Если исходный бакет пуст, `diff` проверяет наличие бакета на приёмнике и возвращает код 1, если его нет.

```bash
./bin/migration diff -c config.yaml --workers 32
./bin/migration diff -c config.yaml --extra
```

```text
=== diff photos ===
ok=1000  missing=2  size_mismatch=0  etag_mismatch=1  extra_on_target=0  size_only=3
一致=1000  缺失=2  大小不一致=0  ETag不一致=1  仅目标有=0  仅比大小=3
  missing  a.txt  not on target
  etag     b.txt  src=abc dst=def
```

Вторая строка сводки повторяет счётчики по-китайски, потому что так печатает команда. Показывается не больше 50 строк проблем; остальное считается в завершающей строке «and N more».

| Результат | Смысл |
| --- | --- |
| `missing` | Ключ есть в источнике, но отсутствует на приёмнике |
| `size` / `etag` | Тот же ключ, содержимое не совпадает. Часто это живая запись на цели. Этот инструмент её не перезапишет |
| `extra` | Только на цели. Сообщается с `--extra`. Обычно запись, которая уже попала на новый кластер. Это не ошибка |

Код выхода 1, если какой-либо ключ отсутствует или не совпадают размер либо ETag. `extra_on_target` команду не проваливает. При нескольких бакетах разрыв проваливает этот бакет, команда продолжает остальные и завершается с 1, если провалился хотя бы один бакет.

## Безопасность

| Гарантия | Как |
| --- | --- |
| Нет перезаписи объекта на цели | `HeadObject` → `PutObject` / `CompleteMultipartUpload` (`If-None-Match: *`) |
| Нет удаления | Нет `DeleteObject`. Неудачная multipart-загрузка только отменяется |
| Нет путаницы бакетов | `HeadBucket`, проверка имени бакета на каждой странице списка и имя бакета в файле SQLite |
| Удаления на источнике во время прогона | Завершённый 404 источника — это `skipped`. Отмена и таймаут — `failed`, они будут повторены |
| Продолжение после сбоя и отмены | Состояние каждого объекта лежит в файле SQLite WAL. Первый сигнал отменяет worker; следующий `migrate` продолжает |
| Память ограничена | Малые объекты идут на диск. Большие читаются по частям. Очередь заданий ограничена |
| Проверка после копирования | Всегда размер. ETag тоже для объекта из одной части, когда оба ETag сравнимы |

Вне области: история версий, маркеры удаления, Object Lock, политики бакета, правила жизненного цикла, двусторонняя синхронизация и серверный `CopyObject` (кластеры разделены, поэтому байты идут через этот процесс).

## Устранение неполадок

| Что видно | Что делать |
| --- | --- |
| `read config … copy config.example.yaml first` | Нет пути `-c`. Скопируйте `config.example.yaml` |
| `old.endpoint is required` | Задайте `old.endpoint` или `OLD_ENDPOINT`. Сторона цели так же сообщает `new.endpoint is required`. Ключи сообщают `access_key` / `secret_key` |
| `workers must be >= 1` | `--workers`, `WORKERS` или YAML `workers` меньше 1. `0` в YAML значит «по умолчанию 16». `0` в CLI или окружении — ошибка |
| `multipart_concurrency must be >= 1` | То же правило для параллельности частей. `0` в YAML значит «по умолчанию 4» |
| `env WORKERS="…" is not an integer` | `WORKERS` должен быть целым без единиц. Полоса задаётся как `RATE_LIMIT=20M` |
| `multipart_part_size must be >= 5242880` | Непоследние части должны быть не меньше 5 MiB. Значение по умолчанию 16 MiB уже годится. Значение само не повышается |
| `unknown size suffix` или `rate limit` | `rate_limit`, `RATE_LIMIT` или `--rate-limit` не распознаны. Десятичное — `20M`. Двоичное — `20Mi` или `20MiB` |
| `head bucket "…"` | Бакета нет, endpoint неверен или ключ не может читать. Ошибка создания на цели говорит `create bucket "…" on target (need s3:CreateBucket)` |
| Источник всё ещё загружен при `20M` | `20M` — это 20000000 байт/с тел, читаемых с источника. Загрузка вне этого потолка. На общей NIC уменьшите число |
| `scan` или `diff` не замедлились | Так и должно быть. Потолок действует, пока `run` / `migrate` читают тела объектов |
| Scan остаётся медленным после повышения `--workers` | Так и должно быть. `scan` однопоточный. Параллельность начинается на копировании и на HEAD у `diff` |
| Много 503 или таймаутов | Снизьте `workers`. Для больших объектов снизьте `multipart_concurrency`, чтобы `workers × multipart_concurrency` уместился в `maxconn` прокси |
| Много результатов `etag mismatch` | Проверьте содержимое объекта отдельно. Разбиение на части и шифрование на сервере могут повлиять на ETag. |
| `db_path is bound to bucket "…"` | Этот файл уже принадлежит другому бакету. Возьмите другой `db_path` |
| `database is locked` | Два процесса пишут одну базу. Один процесс на файл |
| Диск заполняется временными файлами | Перенесите `spool_dir` на большой диск или снизьте `workers` |
| Ctrl-C не возвращает управление | Дождитесь текущего запроса или нажмите ещё раз (код 130) |
| `diff` всё ещё сообщает `missing` | Для `failed` проверьте `last_error` и повторите попытку. Для `done` или `conflict` создайте новую опись в отдельном каталоге. В режиме переноса всех бакетов сменить только имя файла базы недостаточно. |

## Коды выхода

| Код | Смысл |
| --- | --- |
| 0 | Операция завершена. Конфликты и пропущенные объекты учтены отдельно. |
| 1 | Ошибка конфигурации, прерывание, сбой операции или копирования либо `diff` обнаружил отсутствующие или несовпадающие ключи. |
| 130 | Второй `SIGINT` или `SIGTERM`. Процесс завершается сразу |

Ошибки команды печатаются в stderr как `error: …`.
